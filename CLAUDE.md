# DSA & Dev Notes — Project Guide

> **Read this file in full before touching anything in this repo.** It documents non-obvious gotchas (duplicate/parallel systems, a pinned dependency set that OOMs if upgraded carelessly, sidebar wiring that silently swallows new pages) that are not discoverable by reading the code alone and have already caused real, wasted work. If a task looks like "add a new X," check this file for an "Adding a new X" section before improvising — one exists for the four most common tasks (doc page, DSA problem, visualizer, system-design case study).
>
> **For a broader project overview / architecture map, check `graphify-out/`** (repo root — a knowledge-graph snapshot of the codebase from the `graphify` skill, includes `graph.html`/`graph.json`). A second, older, narrower one also exists at `dsa-docs/graphify-out/` — prefer the root-level one, it's the more recent/comprehensive scan. Treat either as a point-in-time snapshot, not a live source of truth — verify anything load-bearing against the actual current code before acting on it.

Personal knowledge base + interactive learning platform: DSA notes/problems, system design, and dev-topic docs (JS, React, Node, SQL, MongoDB, Docker, AI, etc.). Built on **Astro + Starlight**, deployed via Vercel.

**The live app is entirely inside `dsa-docs/`.** Root-level files (`AllDocs/`, `docs/`, `public/`) are not part of the build — `vercel.json` runs `cd dsa-docs && npm install && npm run build`. Always `cd dsa-docs` before running any npm/astro command.

## Stack

- Astro `6.3.1` + `@astrojs/starlight` `0.39.2` (docs framework/sidebar/search) — **pinned, do not upgrade without reading the warning below.**
- React 19 via `@astrojs/react` `5.0.7` (interactive islands: `client:load` / `client:only="react"`)
- Tailwind, MDX, Mermaid (client-side, custom zoom/pan viewer wired in `astro.config.mjs`)
- `npm run dev` (NOT raw `astro dev` — the script sets `NODE_OPTIONS=--max-old-space-size=8192`, required at this project's scale)
- `npm run build`, `npm run preview`

## Architecture gotchas — read before making structural changes

**One giant Starlight `docs` collection.** All content under `src/content/docs/**` (2400+ pages across every topic) is a single Astro content collection named `docs`, hardcoded inside `@astrojs/starlight`'s `docsLoader()` (`node_modules/@astrojs/starlight/loaders.ts`) — collection name and base path are not configurable. You cannot split it into multiple named collections without forking Starlight itself; don't attempt this as a "performance fix," it doesn't reduce total sync cost anyway (whole-site sidebar/search still need everything).

**Cold sync is slow (2-4+ min) on this machine.** After a fresh clone or `.astro` cache wipe, don't test routes until the terminal prints `[content] Synced content` then `watching for file changes...`. Testing before that gives false "collection does not exist or is empty" / 404 errors that look like bugs but aren't. Don't `rm -rf .astro` casually — normal restarts use the persisted cache and are fast; only wipe it if something is actually corrupted.

**Multiple parallel/duplicate systems exist — know which one you're editing:**
- System design: the maintained, actively-improved tree is `src/content/docs/system-design/` (Starlight docs, 11 numbered sections, autogenerated sidebar via `src/config/sidebar-system-design.js`). There is ALSO a separate, older `src/content/docs/hld/` + `src/content/docs/lld/` tree with its own case studies, plus a hand-rolled React dashboard `src/components/system-design/SystemDesignHub.jsx` (mounted at `/system-design` via `src/pages/system-design/index.astro`) that reads from `hld/case-studies`. These do not share content. When asked to improve "system design," confirm which surface the user means — the docs sidebar and the `/system-design` landing page currently show different things.
- DSA problems: the maintained system is `src/data/dsa-problems.js` (`DSA_PROBLEMS` array, rendered by `src/pages/dsa/problems.astro` + `src/components/dsa/DSAProblemList.jsx` / `DSAProblemView.jsx`). A second, separate `/problems` system exists elsewhere in the codebase (auto-glob JSON based) — don't conflate the two.

**Node quirks:** Windows filesystem — watch for AV real-time scanning slowing down file sync (add project folder to Defender exclusions if dev keeps stalling).

**Do not upgrade Astro/Starlight/mdx past `6.3.1`/`0.39.2`/`6.0.3` without care.** This was tried (→ `astro@7.1.6`, `@astrojs/starlight@0.41.5`, `@astrojs/mdx@7.0.5`, `@astrojs/react@6.0.2`) and reverted: `npm run dev` reliably OOM'd (`JS heap out of memory`) even with the 8GB heap flag, sometimes minutes into a fully idle server with zero requests — a dev-mode-only regression, `astro build` was fine on both versions. Root cause was never found (no profiler visibility in this environment); ruled out the Vite dependency-scanner (disabling it via `optimizeDeps.noDiscovery` didn't fix it) and force-pre-bundled `@babel/standalone`. If re-attempting this upgrade, get real memory profiling first (`--inspect` + heap snapshots) rather than guessing at Vite config flags again.

## Adding a new doc page (any dev-topic section: JS, React, Node, SQL, MongoDB, Docker, AI, Angular, Next.js, Python, Redis, TypeScript, AWS, GraphQL, etc.)

1. Create the `.md`/`.mdx` file under `src/content/docs/<topic>/...` — the path segments after `docs/` become the URL. Frontmatter needs at least `title` (required by Starlight's `docsSchema()`); every existing page also sets `description`, and some set `sidebar: { order: N }` — match a sibling file in the same folder for exact conventions (heading style, whether it uses numbered `phase-N-*`/`NN-*` folder prefixes, etc.).

2. **Wire it into the sidebar — do not skip this, it is the single most common way a new page silently goes missing from navigation.** Every top-level topic has its own file at `src/config/sidebar-<topic>.js`, spread together in `src/config/sidebar.js`. These are **not all the same mechanism**:
   - Check which kind yours is: `grep autogenerate src/config/sidebar-<topic>.js`.
   - **If it has `autogenerate: { directory: '...' }`** (true for: ai, angular\*, aws, behavioral, design-patterns, docker, dsa, git, graphql, html-css, interview-prep, javascript, networks, nodejs, python, system-design, tailwind — \*verify per-topic, this list can drift) — dropping a correctly-frontmattered file into that directory is enough; Starlight lists it automatically, ordered by `sidebar.order` if set, else alphabetically.
   - **If it's a fully manual, hand-written list of `{ label, link }` entries** (true for: hld, lld, mongodb, namaste-js, nextjs, oops, react, redis, sql, typescript, and the top-level `sidebar-top.js`) — the page **will build and be reachable by direct URL, but will not appear in the sidebar at all** until you manually add a `{ label: '...', link: '/topic/path' }` entry in the right phase/section block. This has bitten real work before — always grep the topic's sidebar file for a neighboring page's link path first to find where to insert yours.

3. If the topic has a `STRUCTURE_OVERVIEW.md` in its content folder (currently: ai, aws, data-structures, design-patterns, docker, git, graphql, hld, html-css, interview, lld, mongodb, networks, nextjs, nodejs, oops, python, redis, sql, system-design, tailwind, typescript — notably **not** present for angular, behavioral, javascript, namaste-js, nextjs-academy, react, striver-blind-75, so don't invent one for those unless asked), update its file-count/file-list to match — it's a plain human-readable index, not consumed by any build step, but it does go stale and mislead if left unedited.

4. Verify by running `npm run dev`, waiting for the full `[content] Synced content` → `watching for file changes...` sequence (see cold-sync note above — don't judge a 404 before that line prints), then loading the new URL directly **and** confirming it actually shows up in the left sidebar nav (the two are independently breakable, per step 2).

## Adding a new Visualizer (`/visualizer/*`)

This is a **fixed set of ~14 topic-level pages**, not one visualizer per problem or per doc page. To add a new one (e.g. for `trie` or `backtracking`), you need all five of:

1. New component `src/components/visualizers/<Topic>Visualizer.jsx` (model an existing one, e.g. `StackVisualizer.jsx` for a simple one, `GraphVisualizer.jsx` for a complex one).
2. Register it in `VISUALIZER_MAP` in `src/components/visualizers/DSAVisualizerPage.jsx`.
3. Add its metadata to `DSA_TOPICS` in `src/data/visualizers/dsaTopics.js`.
4. New page `src/pages/visualizer/<topic>.astro` (copy `sorting.astro`, change `topicId` and the `<title>`/meta description).
5. Add a link in `src/components/visualizers/VisualizerSidebar.jsx`.

This is a real feature addition (a new animated component), not a config toggle or a content-only change — don't attempt it as a quick add unless a visualizer is actually what's being asked for.

Structure, for reference when modifying an existing one instead of adding a new one:

- `src/pages/visualizer/<topic>.astro` — thin page, renders `<DSAVisualizerPage topicId="..." client:load />`.
- `src/components/visualizers/DSAVisualizerPage.jsx` — looks up `topicId` in `VISUALIZER_MAP` (top of the file) and `DSA_TOPICS` (`src/data/visualizers/dsaTopics.js`).
- `src/components/visualizers/<Topic>Visualizer.jsx` — the actual animated component.
- `src/components/visualizers/VisualizerSidebar.jsx` — nav between topic pages.

**Important: the DSA Playground and the Visualizer are NOT linked to each other.** Adding a DSA problem does not automatically surface it in any visualizer, and there's no "topics → visualizer" auto-routing — `DSA_PROBLEMS.topics` values (see the fixed vocabulary below) and `VISUALIZER_MAP` keys are two independently-maintained vocabularies that only partially overlap (e.g. `binary-search`, `sliding-window`, `backtracking`, `greedy`, `trie`, `topological-sort`, `bit-manipulation` currently have NO dedicated visualizer at all). If a new DSA problem's topic already has a visualizer, no visualizer work is needed for it — it just won't be automatically featured there, and that's expected/fine. Don't assume adding a problem with topic `"trie"` gives it a visualizer — it doesn't.

## Adding a new DSA problem (`/dsa/problems`)

Add an entry to the `DSA_PROBLEMS` array in `src/data/dsa-problems.js`. Required shape (match an existing recent entry, e.g. `two-sum` or `implement-queue-using-stacks`, for exact field formatting):

```js
{
  id: "kebab-case-slug",              // unique, used as URL slug and React key
  number: N,                          // MUST be globally unique across all 100+ entries — see below
  title: "Human Title",
  difficulty: "Easy" | "Medium" | "Hard",
  topics: ["arrays", "hash-map", ...],// see the fixed topic vocabulary below
  companies: [...], acceptance: N, xp: N,
  problemStatement: "...", examples: [...], constraints: [...],
  conceptOverview: "...", patternRecognition: "...",
  sampleTests: [ { name, input: [...args], expected } ],   // REQUIRED — see below
  starterCode: "...",
  hints: [...],
  bruteForceSolution: { code, timeComplexity, spaceComplexity, explanation },
  optimizedSolution: { code, timeComplexity, spaceComplexity, explanation },
  interviewExplanation: "...",
  tests: [ { name, validate: (code) => boolean } ],  // see below
}
```

**`number` must be unique.** Check before picking one:
```bash
node --input-type=module -e "
import { DSA_PROBLEMS } from './src/data/dsa-problems.js';
console.log(Math.max(...DSA_PROBLEMS.map(p=>p.number)));
"
```
Numbers 1-71ish are a custom sequential range; 62+ also overlaps with real LeetCode question numbers used for later-added problems (e.g. `1143` = LCS) — that's intentional for recognizable problems, just don't collide with an existing one.

**`sampleTests` is the preferred, real test path.** These run in a sandboxed Worker (`src/workers/js-judge.worker.js`) via `execWorker` in `DSAProblemView.jsx` — actual function execution, with a timeout that hard-kills a hanging submission. Always add real `sampleTests` for a single pure function (`functionName(...args) → return value`) style problem. `compareMode` on the problem object controls comparison (`exact` default; check `js-judge.worker.js` for other supported modes if the answer isn't a simple deep-equal, e.g. order-independent).

**`tests` (legacy `validate()` closures) — for class/stateful problems only, or extra edge cases.** Use this when the problem needs multiple stateful method calls (e.g. `MyQueue`, `MinStack`, `LRUCache`) that don't fit the single pure-function `sampleTests` shape. These now run in a sandboxed Worker too (`src/workers/dsa-legacy-judge.worker.js`), so a hanging submission won't freeze the tab — but the *content* of each `validate` closure is entirely on you to get right. Hard rules, learned from real bugs found and fixed in this file:

- **Every `validate` must actually execute the submitted code and check a real return value**, via `new Function(code + "; <call it>; return <result>")() === <expected>`. Wrap in try/catch, return `false` on throw.
- **Never use `testContains("keyword")` or `anyTest(...)` string-matching as a gate for Accepted.** These were used ~12 times in this file for "did you use pattern X" checks (e.g. `testContains("push(") && testContains("pop(")`) and were all removed or rewritten after finding: (a) a JS operator-precedence bug — `testContains(a) && testContains(b)` evaluates to just the second function, silently dropping the first check entirely; (b) they're trivially gamed by a comment containing the keyword; (c) they unfairly fail a **correct** submission that solves the problem a different way (proven: this file's own `bruteForceSolution` for several problems doesn't contain the "required" keyword and would have failed its own check). If you want to test "did they use the intended technique," design a behavioral test that only a correct implementation of that technique can pass (e.g. `min-stack`'s real fix: push duplicate minimums, pop through them, assert `getMin()` stays correct at each step — no naive/wrong implementation can fake this, and a valid alternative approach isn't penalized for using different variable names).

**Verification standard before considering a new/edited test "done" — do all of these:**
```bash
cd dsa-docs
node --input-type=module -e "
import { DSA_PROBLEMS } from './src/data/dsa-problems.js';
const p = DSA_PROBLEMS.find(x => x.id === 'YOUR-ID');
console.log('vs optimizedSolution (must be ALL PASS):');
p.tests.forEach(t => console.log(t.validate(p.optimizedSolution.code) ? 'PASS' : 'FAIL', t.name));
console.log('vs bruteForceSolution (must also be ALL PASS if it is real runnable code):');
p.tests.forEach(t => console.log(t.validate(p.bruteForceSolution.code) ? 'PASS' : 'FAIL', t.name));
"
```
Also syntax-check the whole file fast (don't wait on a full `astro build` for a data-only change):
```bash
node -e "require('esbuild').transformSync(require('fs').readFileSync('src/data/dsa-problems.js','utf8'), {loader:'js'})" && echo OK
```

**Fixed topic vocabulary currently in use** (keep new problems within this set unless you're deliberately introducing a new category — see the "Adding a new Visualizer" section above for why that matters): `arrays, strings, hash-map, two-pointers, sliding-window, stack, queue, linked-list, trees, graphs, heap, recursion, dp, backtracking, greedy, binary-search, bit-manipulation, topological-sort, trie, sorting`.

## System design case studies (`src/content/docs/system-design/11-case-studies/`)

20 case studies, sidebar order 1-20 via frontmatter `sidebar.order`. House style (match `design-url-shortener.md` or `design-distributed-lock-service.md` for exact formatting):

Frontmatter (`title`, `description`, `sidebar.order`) → `# Case Study: <Title>` → `>` blockquote one-liner → `---` → `## Requirements` (Functional/Non-functional) → optional `## Estimation` table → optional `## API Design` → `## Data Model` (SQL) → `## High-Level Design` (mermaid `flowchart LR`, color palette `#7c3aed #4f46e5 #6366f1 #8b5cf6 #059669`) → 2-4 `## Deep Dive: <Topic>` sections (mermaid `sequenceDiagram`s, short code, tables) → `## Bottlenecks & Trade-offs` table → `## Follow-up Questions` (4-6 `**Q: ...**` pairs) → `## In Simple Words` (3-4 bullets).

Before adding a new case study, check it doesn't duplicate an existing one's core technique — several were deliberately scoped to avoid overlap (e.g. `design-proximity-service.md` explicitly contrasts itself against `design-ride-sharing.md`'s moving-point Redis-geo approach; `design-distributed-key-value-store.md` contrasts against `design-distributed-cache.md`'s in-memory-only model).

New case study files are picked up automatically by the sidebar (`autogenerate` in `src/config/sidebar-system-design.js`) — no manual sidebar edit needed. Do update `src/content/docs/system-design/index.md`'s "Case Study Quick Reference" table and `STRUCTURE_OVERVIEW.md`'s file count/list when adding one.
